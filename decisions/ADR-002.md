# ADR-002 — Persistence ports for transactional order placement
**Team 10 · 9 October 2026 · Status: Proposed (reconciled with accepted ADR-001)**

**Trace:** UC-01, FR-05/06/07/12, AC-01–05, QS-01/03/09; Lab 8 `docs/api-contracts/core-operation.md` and `models/logical-data-model.md`.

## Context
ADR-001 has already **accepted** the modular monolith, single relational store, and `placeOrder` transactional boundary. Lab 8 already defined an `Order.idempotencyToken UNIQUE`, derived `Listing.availableQuantity`, stable HTTP error codes and same-body 201 replay. ADR-002 is deliberately narrower: choosing internal boundaries, **not** reopening ADR-001 or introducing a separate idempotency database model.

## Decision
Define repository ports for Listing, Order and OrderStatusEvent plus a transaction-scoped `UnitOfWork`. Implement `PlaceOrderService` against these stable interfaces. `findByIdempotencyToken()` checks existing committed orders; reserve available stock with row locking or a guarded update; save the new Order (carrying the globally unique token) and its initial status event; commit all or roll back all. If a concurrent duplicate token causes unique violation, roll back and fetch the committed winner safely. The HTTP adapter preserves Lab 8 `POST /orders` request, success/error response and replay rules. Stub SMS/routing adapters run only after commit and cannot change order correctness.

## Options and explicit rejection
- **Alternative:** put SQL in the HTTP controller. Less code upfront, but couples protocol behavior, stock rules and persistence, complicating test isolation.
- **Rejected for this slice:** Strategy, Factory, or distributed Saga infrastructure without a named variable algorithm/object-creation problem; the added indirection offers no concrete benefit. Independently deployed microservices were already rejected in ADR-001, so ADR-002 does not present their rejection as a new architectural decision.

## Consequences
+ Clear dependency direction and transaction-scoped ports; direct mapping to Lab 8 logical model/API.
+ Mockable interfaces for component tests; real relational DB still required to prove no oversell or duplicate orders.
- Additional types/adapters, transaction-scoping discipline and database contention under simultaneous orders.
- The Lab 8 replay policy for altered payload with an existing token remains **unspecified**; resolve separately before implementing that edge case.

## Verification and exit record
**Highest-benefit boundary:** transaction-scoped Listing/Order/OrderStatusEvent persistence. **Cost:** extra adapter interfaces and lock contention. **Test:** simultaneous competing orders in AC-04/QS-01 must never oversell; AC-05/QS-03 retry must preserve original response; QS-09 crash tests must preserve committed status history. These are planned tests, not passed results.
