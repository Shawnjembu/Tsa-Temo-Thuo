### UC-01: Place OrderTeam 10 — Tsa Temo Thuo · CSI473 Lab 3 · 14 August 2026Traces to: FR-05, FR-06, FR-07, FR-09 · Objective 2 (stock integrity) · Proposed core workflow steps 2–3 (proposal §6)##### Primary actorBuyer (restaurant, small retailer or street trader)##### Secondary actorsFarmer (owns the listing; notified of the new order)System (validates the order and atomically manages stock reservation)##### Stakeholders and interestsBuyer — wants the chosen quantity of produce reliably reserved when the order is placed, rather than merely recorded as a request.Farmer — wants listed stock to never be oversold and wants to see only orders that are supported by available stock.Administrator — wants every order state change and relevant stock change persisted for monitoring and reporting.#### Preconditions\- The buyer is registered and Verified (FR-02).\- At least one listing exists in the Active state.\- The listing has available quantity greater than zero (FR-03, FR-09).\- The listing has not passed its availability window.\- The produce listing contains the required information, including crop, grade/quality classification, unit price, available quantity, district and availability window.#### Postconditions (success guarantee)\- An Order record exists in the Placed state and is linked to the buyer and the farmer's listing.\- The ordered quantity has been moved from available stock to reserved stock.\- The listing's available quantity has been reduced by exactly the ordered quantity.\- The listing's total quantity has not been changed.\- The reservation is atomic, so concurrent orders cannot reserve the same stock.\- The farmer can see the new order against their listing.\- The order's creation timestamp and relevant stock state are persisted.###### ###### Stock rule:Available + Reserved + Confirmed = TotalReserved + Confirmed ≤ TotalWhen an order is later confirmed, its quantity moves from Reserved to Confirmed. It is not deducted from Available stock a second time.TriggerThe buyer submits a valid quantity against a specific Active listing.###### ##### Main success scenario1\. The buyer searches Active listings (UC — Search Listings) and selects a listing.2\. The buyer views the listing details, including the farmer-declared produce type, grade/quality information, price, district and available quantity.3\. The buyer enters a desired quantity and submits the order.4\. The system verifies that the listing is still Active and that the requested quantity does not exceed the listing's current available quantity.5\. The system atomically reserves the requested quantity against the listing.6\. The system creates the Order in the Placed state and records the reservation as part of the same successful transaction.7\. The system records the order's creation timestamp and links the order to the buyer and farmer's listing.8\. The system notifies the farmer that a new order is awaiting confirmation.9\. The buyer sees an on-screen confirmation showing the order in the Placed state and the quantity reserved.10\. The farmer may subsequently confirm or reject the order.##### Extensions (alternative and exception flows)**3a. Requested quantity exceeds available quantity**3a1. The system rejects the order without creating a reservation.3a2. The system does not create a valid Order record.3a3. The system returns a message stating the actual quantity currently available.3a4. The buyer may resubmit with a smaller valid quantity.3a5. The listing's stock remains unchanged.Use case ends in failure.**3b. The listing is no longer Active**3b1. The system detects that the listing is Sold Out or Expired.3b2. The system rejects the order without creating a reservation.3b3. The system returns a message stating that the listing is no longer available.3b4. The buyer is returned to Search Listings.Use case ends in failure.**4a. Concurrent orders compete for the last remaining stock**4a1. Two or more buyers submit orders whose combined quantity exceeds the available quantity at approximately the same time.4a2. The system performs the reservation as an atomic operation.4a3. Only orders that can be fully supported by the available quantity are accepted.4a4. The remaining orders are rejected using the same validation path as 3a.4a5. No partial or corrupted stock state results.4a6. The combined Reserved and Confirmed quantities never exceed the listing's Total quantity.Use case ends with one or more controlled successes and controlled failures, depending on the available quantity and requested quantities.**4b. The buyer's device retries the submission after a dropped connection**4b1. The buyer's device loses connectivity after submitting the order but before receiving the response.4b2. The buyer's client retries the request using the same client-generated idempotency token.4b3. The system recognises the token as an existing request.4b4. The system does not create a second Order or second stock reservation.4b5. The system returns the original order and its current state to the buyer.Use case ends in success without duplication.**5a. Farmer rejects a placed order**5a1. The farmer reviews a Placed order and rejects it.5a2. The system changes the Order state to Rejected.5a3. The system releases the reserved quantity.5a4. The released quantity is returned to the listing's Available quantity.5a5. The system does not change the listing's Total quantity.5a6. The released quantity becomes available for a subsequent valid order.**5b. Buyer cancels a placed order**5b1. The buyer cancels an order while it is still in the Placed state.5b2. The system changes the Order state to Cancelled.5b3. The system releases the quantity reserved for the order.5b4. The released quantity is returned to the listing's Available quantity.5b5. The cancelled order no longer holds a reservation.**5c. Reservation expires before farmer confirmation**5c1. A Placed order remains unconfirmed until the configured reservation period expires.5c2. The system changes the order to Expired.5c3. The system releases the reserved quantity.5c4. The released quantity is returned to the listing's Available quantity.5c5. The released quantity can subsequently be reserved by another valid order.**6a. Farmer confirms a placed order**6a1. The farmer confirms a Placed order.6a2. The system changes the Order state from Placed to Confirmed.6a3. The reserved quantity is transferred from Reserved stock to Confirmed stock.6a4. The system does not deduct the quantity from Available stock again.6a5. The listing's stock remains consistent according to:Available + Reserved + Confirmed = Total6a6. If Available quantity is now zero, the listing changes to Sold Out.**7a. Produce-quality information or grade is disputed**7a1. A buyer reports that delivered produce does not match the grade or quality information declared in the listing.7a2. The system associates the complaint with the relevant order, listing and farmer.7a3. The system identifies the farmer as responsible for the accuracy of the produce information and grade declared in the listing.7a4. The system does not represent the platform as independently guaranteeing the physical quality of the produce.7a5. The dispute is made available for the appropriate administrative review process.#### Special requirements\- The stock-reservation operation must be implemented as a single atomic data-layer operation, rather than a read-then-write sequence in application code.\- The reservation operation must prevent concurrent requests from reserving the same stock.\- The system must maintain the stock relationship:&#x20; Available + Reserved + Confirmed = Total\- A confirmed order must not deduct reserved stock from Available stock a second time.\- Rejected, cancelled and expired reservations must be released back to Available stock.\- The system must prevent negative Available stock.\- The system must prevent Reserved + Confirmed from exceeding Total stock.\- Rejection messages must state the actual available quantity where applicable.\- Order submission must support an idempotency token to prevent duplicate orders and duplicate reservations after connectivity failures.\- The farmer is responsible for accurately declaring the produce type, grade/quality and other listing information. The system records and displays the farmer-declared information but does not independently guarantee physical produce quality.#### FrequencyExpected to be the single most frequent transaction in the system and the core transaction of the Phase 2 vertical slice.#### Open issueThe specific reservation expiry duration must be agreed and documented before implementation. The duration should be configurable rather than hard-coded into the use case.The administrator's reporting requirements for rejected, cancelled and expired orders should also be confirmed as part of the reporting requirements, while the order state changes themselves must remain persisted for auditability.
