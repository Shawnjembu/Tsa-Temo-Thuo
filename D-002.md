# D-002: Two domain-modelling choices — Lab 4

Team 10 — Tsa Temo Thuo · CSI473 Lab 4 · 21 August 2026

## Choice 1 — Model order-state history as a separate `OrderStatusEvent` class

**Decision:** `Order` composes `0..*` `OrderStatusEvent` records. Each state
change appends one immutable event (fromState, toState, occurredAt) instead
of `Order` overwriting a single `state` field in place.

**Alternative considered:** Keep only `Order.state` and leave history to
infrastructure — application logs or a database audit trigger sitting
outside the domain model.

**Consequence accepted:** The domain model gains a class that exists purely
to record history, which is one more thing to keep consistent. We accepted
this because BR-10 ("order state changes are appended, never overwritten")
is a domain rule the team already committed to, not an infrastructure
concern — FR-12 (view full status history) and QS-09 (recoverability after
a crash) both need that history to survive independently of any one
server's logs. Leaving it to infrastructure would mean the invariant BR-10
describes isn't actually enforceable at the model level; nothing would stop
a future implementation from mutating `Order.state` in place and quietly
losing history.

## Choice 2 — Verification status stays a single attribute on `Account`, not a separate `Registration` class

**Decision:** `Account.verificationStatus` (Pending/Verified/Rejected)
remains one attribute on the abstract `Account` superclass shared by
`Farmer` and `Buyer`.

**Alternative considered:** A separate `Registration` entity (submitted
verification details, decision, reviewing administrator, decision
timestamp, rejection reason) in a 1-to-1 relationship with `Account`,
mirroring FR-02's requirement to record a reason when rejected.

**Consequence accepted:** We're not yet capturing *who* verified an account,
*when*, or *why* a rejection happened as first-class, queryable data — just
the current status. We accepted this rather than modelling `Registration`
now because no acceptance criteria or quality scenario currently exercises
that audit detail (FR-01/FR-02 have no drafted use case or AC yet — see
`docs/traceability-matrix.md`), and the lab brief's design trap warns
against modelling ahead of confirmed evidence needs. If FR-02's "reason
when rejected" becomes evidence the portfolio needs to show, `Registration`
is the documented fallback and this decision should be revisited then.
